Took a look — before this goes anywhere near `review/run.ts` I'd hold off, there are a few things here that go deeper than nits.

**The two imports at the top are the biggest problem.** `import type { FastifyRequest } from 'fastify'` (line 3) pulls a web-framework type straight into reviewer-core, which is supposed to be the framework-free domain package. Even as a type-only, optional, unused parameter (`req?: FastifyRequest` on line 23 — it's never referenced in the body), it means this module now has a compile-time dependency on Fastify. If `scoreRisk` ever needs something from the request, that's a sign the data should be extracted at the HTTP layer and passed in as plain data, not that the domain function should reach for the request object itself.

Line 4 is worse: `import type { PullRow } from '../../../server/src/db/rows.js'` reaches across a relative path out of reviewer-core into server's internal db module. A few problems stack up here:
- reviewer-core and server are separate packages with their own package.json/lockfile — a relative import that crosses that boundary is exactly what the tsconfig path-alias convention exists to avoid, and I'd be surprised if this even resolves cleanly under reviewer-core's own tsconfig/build (its rootDir almost certainly doesn't include `../../../server`).
- Even if it did resolve, it inverts the dependency direction — reviewer-core's `RiskScoreInput` now depends on server's DB row shape, so a migration to `PullRow` (which you're not supposed to hand-edit anyway per the do-not-touch list) can silently break the domain layer. `RiskScoreInput` should take its own minimal shape (e.g. `{ owner: string; repo: string }`) rather than the full row.

**The network call is the part I'd push back on hardest.** `fetchFanInFromGitHub` (lines 31–37) hits `https://api.github.com/repos/{owner}/{repo}/contents` live, from inside what's supposed to be a pure scoring function. A few issues, in order of how much they'll actually bite:

1. That endpoint returns the *root directory listing only* — it's not recursive. So `contents.some((c) => c.path === p)` will only ever match paths that live at repo root; any nested file (`src/foo/bar.ts`, which is the overwhelming majority of real diffs) will never match, `fanIn` will be ~0, `spread` will be ~0, and the "how central are the touched files" signal you're trying to build just won't exist in practice. This isn't a style issue, it's the feature not doing what the docstring says it does.
2. No auth header — unauthenticated GitHub API calls are capped at 60 req/hour per IP, and private repos will 404/403 outright. For something meant to run per-PR, this will start failing almost immediately in real use.
3. No `res.ok` check before `res.json()`. On a rate-limit or error response the body won't be a `{ path }[]` array — it'll be something like `{ message: "..." }` — and `contents.some(...)` will throw. That exception propagates straight out of `scoreRisk` with no fallback, so a transient GitHub hiccup takes down the whole review, not just the risk score.
4. Doing this over the network at all cuts against the project being local-first (per the root CLAUDE.md description) — this reaches out to github.com on every score, is non-deterministic, slow, hard to unit test without mocking global `fetch`, and hardcodes `api.github.com` so it won't work against GitHub Enterprise.

Also, naming/semantics: the docstring talks about files that "fan out," the function is named `fetchFanInFromGitHub`, and what it actually computes is neither fan-in nor fan-out in the graph sense — it's just "is this path present in the repo root." Worth deciding what centrality metric you actually want (import fan-in count, blast-radius from an existing precomputed graph, etc.) and naming/implementing that directly, rather than working backward from what a single unauthenticated API call happens to give you.

**What I'd change before wiring it in:**
- Drop the `FastifyRequest` param entirely.
- Replace the `PullRow` import with a narrow local type for what this function actually needs (owner/repo strings), or take it as an already-extracted plain object.
- Pull the "how central is this file" computation out of `scoreRisk` and behind an injected dependency (a small interface reviewer-core defines, implemented/adapted at the server layer if a network or precomputed-graph lookup is genuinely needed) — that keeps the domain function pure, synchronous-testable with a stub, and cacheable by whoever owns the adapter. `scoreRisk` itself shouldn't know whether centrality comes from GitHub, a local git blame, or a static import graph.
- If you do keep an HTTP call in the mix somewhere, it needs `res.ok` handling and a fallback (e.g. treat fetch failure as `fanIn = 0` rather than throwing) so a transient network issue degrades the score instead of breaking the review.

The severity-weight table and the final `base * (1 + spread)` formula are fine as they stand — `spread` is correctly bounded to [0, 1] since `fanIn` can't exceed `paths.length`, and the empty-diff guard on line 27 is a nice touch. It's really the data-sourcing side that needs to change before this is safe to call from `review/run.ts`.
