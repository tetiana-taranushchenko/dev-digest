Here's my review of the webhooks module draft.

**routes.ts imports `repository.ts` directly and uses it before the service ever runs.** Lines 5 and 17 (`import { WebhooksRepository } from './repository.js'` and `const repo = new WebhooksRepository(app.container.db)`), then the handler calls `repo.findByDeliveryId(deliveryId)` directly at lines 23-27 to short-circuit on dedup. That's the exact thing the skill calls out as CRITICAL: routes.ts must never import `repository.ts`, and must never contain business rules — it parses/validates and delegates to the service. Dedup is a business rule (what counts as "already processed"), and it belongs entirely inside `WebhooksService.handleDelivery`, which already re-implements the same check at service.ts lines 28-29. Right now you have the same invariant duplicated in two layers, plus a real side effect: because the route's dedup check runs *before* the service is ever called, a request with a known/guessed `x-github-delivery` value gets a 200 without the HMAC signature ever being verified — the signature check only lives inside `handleDelivery`, which the dedup path skips. Move the dedup check into the service (or drop it from the route and let the service's own check be the single source of truth) and have the route call `service.handleDelivery` unconditionally.

**service.ts reaches into Drizzle directly instead of going through the repository.** Lines 5-7 import `db` and `t` (schema) and `eq` from the db layer, and lines 32-35 run a raw `db.select().from(t.workspaces).where(...)` inline. The skill is explicit: "`service.ts` never imports Drizzle `db`/`schema` directly — only through `repository.ts`'s exported functions/types. If a service needs a new query, add a function to `repository.ts`." Add something like `findWorkspaceById` to `WebhooksRepository` (or reuse the workspace module's repository if one already exists) and call that instead — this is what makes the service unit-testable without a real database, which is the whole point of the split you already chose.

**The HMAC verifier is wired ad hoc inside the service instead of through the composition root.** `service.ts` line 15 does `this.verifier = new HmacWebhookVerifier(secret)` inside the constructor. `hmac-verifier.ts` already defines a `WebhookVerifier` interface specifically so implementations can be swapped — but by instantiating the concrete class inside `WebhooksService`, you've bypassed that. This is the composition-root rule (MEDIUM, but concretely painful): `server/src/platform/container.ts` is supposed to be the only place a port and its concrete adapter are wired together, mirroring how `git`, `github`, `secrets`, etc. are exposed as `container.<name>` getters with `ContainerOverrides` support for tests. As written, there's no way to inject a fake verifier in a service-level unit test without monkeypatching the module. Add a `webhookVerifier` (typed as `WebhookVerifier`) to `Container`/`ContainerOverrides`, construct the real `HmacWebhookVerifier` there, and have `WebhooksService` take it from `container.webhookVerifier` instead of building its own.

**The webhook secret bypasses `SecretsProvider`.** routes.ts line 16 reads `process.env.WEBHOOK_SECRET ?? ''` directly. Every other secret in this codebase (`GITHUB_TOKEN`, `OPENAI_API_KEY`, `OPENROUTER_API_KEY`) goes through `container.secrets.get(...)` (see `container.ts`'s `github()`/`buildLlm()`), and a missing key throws a `ConfigError` rather than silently falling back to an empty string. An empty-string secret here means every signature check will simply fail against an HMAC of `''`, which is a confusing way to discover misconfiguration. Resolve it via `container.secrets.get('WEBHOOK_SECRET')` and fail loudly (`ConfigError`) if it's unset, same as the other adapters.

**Error handling doesn't use this repo's error taxonomy.** service.ts throws plain `Error('invalid signature')` (line 25) and `Error('unknown workspace')` (line 36). `platform/errors.ts` has `AppError`/`ValidationError`/`NotFoundError`/`ConflictError` etc., each carrying a `statusCode` that the global error handler maps to the right HTTP response. A bare `Error` here will fall through to whatever the default handler does with an unrecognized error (likely a generic 500) instead of, say, a 401 for a bad signature or a 404 for an unknown workspace. Swap these for the appropriate `AppError` subclasses.

**Minor duplication:** `WebhooksRepository` gets instantiated twice with the same `db` — once in routes.ts (line 17) and again inside the service constructor (service.ts line 14). Once you remove the route's direct repository use, this goes away on its own.

On the parts that are fine: the graduated-layering call to give this module a full `routes → service → repository` split (plus the `hmac-verifier` adapter) is correct — it's coordinating a signature check, a dedup lookup, and a workspace-existence check before persisting, which clears the "makes a decision / coordinates multiple sources" bar. And validation placement is right in spirit: Zod (`DeliveryHeaders`) validates shape at the boundary (including correctly leaving the signature header optional at the shape level rather than trying to encode "must be a valid signature" as a `.refine()`), while the actual signature check is business logic living in the service — that pattern just needs the wiring fixes above to actually hold together.

Net: before this goes into `modules/index.ts`, I'd fix the route→repository bypass and the service→db bypass (both CRITICAL per the skill), then wire the verifier and secret through the container the way the rest of the adapters are.
